# レビュースキル設計書 — statusline-review

作成日: 2026-08-02

## この文書は何か

`@chieeeeno/claude-statusline` リポジトリに、機能追加時のコードレビューを自動化する仕組みを置くための設計。スキル 1 つとサブエージェント 2 つで構成し、PR に対してレビュー・修正・再レビューのループを回して最終的に LGTM を出すところまでを担う。

対象はこのリポジトリのみ。他プロジェクトへの流用は想定しない。

## なぜ作るのか

実装したその文脈のままレビューすると、「ここはこう書いたから正しいはず」という思い込みを持ち込む。レビューを独立した文脈に切り出すことで、差分とリポジトリだけを根拠に判断させる。

品質とセキュリティを別エージェントに分けるのは、1 つのプロンプトに両方を載せると注意予算が品質側に流れ、セキュリティの検査が薄くなるため。分離することで、セキュリティ側を「攻撃者としてどう悪用するか」という別の思考モードに固定できる。

このパッケージは **npm で配布され、利用者の `~/.claude/settings.json` を書き換え、そこに書いたコマンドが利用者の環境で毎分実行される**。壊し方を間違えると利用者の環境を壊す。セキュリティを厳重に見る理由はここにある。

## 構成

```
.claude/
├── skills/
│   └── statusline-review/
│       └── SKILL.md              オーケストレータ（/statusline-review で起動）
└── agents/
    ├── quality-reviewer.md       コード全体の品質チェック
    └── security-reviewer.md      セキュリティ専門

docs/                             リポジトリに追跡する
├── 01-review-skill-design.md     この文書
└── 02-code-review-criteria.md    審査項目の唯一の情報源。両エージェントが実行時に読む

handover/                         .gitignore で除外（手元にのみ残す）
├── 00〜03, 99                     dotfiles からの引き継ぎ資料
└── artifacts/                     実測値を含むため公開しない
```

ファイル名を ASCII にしているのは、エージェントがパス指定でこの文書を読むため。日本語のファイル名はシェルやツールをまたぐ際に扱いが崩れやすい。

`.claude/` 配下は「どう動くか」、`docs/02` は「何を見るか」を持つ。両エージェントは起動時に `02` を読む依存関係があるため、**`02` はリポジトリに追跡されていなければならない**。追跡されていないと、クローンした環境でレビューが機能しない。

引き継ぎ資料を `handover/` へ分けたのはこのため。当初は `docs/` ごと除外していたが、レビューの動作に必要な文書を `docs/` に置くことになった時点で、除外の単位を「公開しない資料」側へ移した。`handover/artifacts/statusline-payload.json` には `session_id` と `transcript_path` の実測値が入るため、これは公開してはならない。

スキル名を `statusline-review` にするのは名前の衝突を避けるため。環境には既に `/review`（GitHub PR レビュー）と `/code-review`（作業差分のレビュー）があり、汎用的な名前を付けると意図しない方が起動する。

エージェント 2 つはスキル経由でも単体でも呼べる独立した定義にする。「今回はセキュリティだけ見たい」という使い方を残すため。

## 実行フロー

### 準備段階

1. `gh auth status` とリモート設定を確認する。**未認証またはリモート未設定なら停止する。** リモートの作成（`gh repo create`）はこのスキルの責務ではない。外部に公開リポジトリを作る操作をレビューの副作用として行わないため
2. 対象 PR を決める
   - 現在のブランチに紐づく PR があればそれを使う
   - なければ `main` からブランチを作成し、変更をコミットして push し、**draft PR を作成する**
3. ベースブランチを決める。PR の base → なければ `origin/HEAD` → なければ `main`
4. `git diff <base>...HEAD --name-only` で対象ファイルを確定する。空なら停止する

3 点ドット（`<base>...HEAD`）を使うのは、マージベース起点の差分を取るため。2 点ドットだとベースブランチ側の進行がノイズとして混ざる。

**前提**: このスキルは GitHub リモートと `gh` の認証が済んでいることを要求する。したがって初回は、リポジトリの作成と `main` の push を先に済ませておく必要がある。

### レビューループ（最大 3 周）

| 手順 | 内容 |
| --- | --- |
| a | 品質・セキュリティの 2 エージェントを**並列起動**する。同じ差分とベース情報を渡す |
| b | 各エージェントは検証を自分で走らせ、**裏付けの取れた指摘だけ**返す |
| c | `file:line` で重複排除し、重大度順に統合する |
| d | 行単位インラインコメントと総評を PR に投稿する |
| e | **Blocker とセキュリティ High 以上が 0 件なら** LGTM 総評を投稿して終了する |
| f | 残っていれば修正 → `npm test` → コミット → push → 次の周へ |
| g | 修正した指摘のスレッドに返信し、**解決済みにして折りたたむ** |

修正対象は **Blocker とセキュリティ High 以上に限る**。Should fix 以下と Medium 以下は報告するだけでループを回さない。ここを緩めるとリリースに関係のない改善で永久に回り続ける。

**修正はスキルのメインループが行い、レビューエージェントには書かせない。** 指摘した本人が直すと、直したことで指摘が正しかったことにしてしまう。レビューと修正は分けておく。

**投稿の実装**: 行単位のインラインコメントは `gh api` で pull request review を作成し、`comments[]` に `path` / `line` / `body` を渡す。総評は同じ review の `body` に載せる。1 回の API 呼び出しで両方が投稿されるため、インラインだけ付いて総評が抜ける中途半端な状態にならない。

## 安全弁と停止条件

- **3 周で打ち切る。** 残った指摘を「未解決」として総評に列挙し、**LGTM は出さない**
- **修正後に `npm test` が落ちたら、その周の修正を戻して停止する。** 壊れたコードを push しない
- **同じ指摘が 2 周連続で残ったら、総評にその事実を明記する。** 直せていないことを隠さない
- **実際の `~/.claude/settings.json` には絶対に触らない。** CLI の挙動検証は `HOME=$(mktemp -d)` で行う

修正も投稿も自動で行う。スキルの起動をループ全体の承認とみなす。対象が draft PR なので影響範囲は限定される。

## エージェント仕様

### 審査項目は別文書に置く

**審査項目の唯一の情報源は `docs/02-code-review-criteria.md`。** 両エージェントはレビュー開始時にこの文書を読んでから差分を見る。エージェント定義側に項目を複製しない。

分離する理由は 2 つ。観点を足すときに 2 つのプロンプトを両方直す必要がなくなること、そして 2 つのエージェントが同じ重大度定義と同じ検証手段を共有することで、統合時に基準がずれないこと。

| 文書の章 | 読む主体 |
| --- | --- |
| 1. このパッケージについて | 両方 |
| 2. 共通の規律 | 両方 |
| 3. 重大度の定義 | 両方 |
| 4. 品質観点 | `quality-reviewer` |
| 5. セキュリティ観点 | `security-reviewer` |
| 6. 検証手段 | 両方 |
| 7. 指摘しないもの | 両方 |

担当外の章を読むこと自体は妨げないが、担当外の指摘は出させない。重複指摘は統合時のノイズになる。

### quality-reviewer

`02` の第 4 章「品質観点」を担当する。このパッケージの不変条件を審査軸にし、汎用のコード品質論ではなく *このパッケージが壊れる特定の壊れ方* を見る。重大度は Blocker / Should fix / Consider。

### security-reviewer

`02` の第 5 章「セキュリティ観点」を担当する。攻撃者視点に固定し、コマンド注入と `settings.json` 汚染、機微情報の漏えい、サプライチェーン、ファイル操作・実行の安全性の 4 領域を見る。重大度は Critical / High / Medium / Low で、**High 以上がループの継続条件**になる。

### 検証手段

両エージェントに Bash を与え、報告する前に自分で確かめさせる。具体的なコマンドと期待値は `02` の第 6 章にまとめてある。

### エージェント定義に書くこと

観点を `02` に出した結果、エージェント定義側に残るのは以下だけになる。

- 役割と担当章の指定（「`docs/02-code-review-criteria.md` を読み、第 N 章を担当せよ」）
- 出力形式（重大度・`file:line`・再現シナリオ・検証結果）
- 思考モードの固定（セキュリティ側は攻撃者視点）
- 担当外の指摘を出さないこと

## PR コメントテンプレート

投稿は毎回この書式に沿う。書式が揺れると周回ごとの比較ができなくなる。

以下の雛形に出てくる件数・時間・ファイル名（`34 件`、`0.46 秒`、`file:line`）はすべて記入例であり、実際の測定値で置き換える。

### 総評（要修正時）

```markdown
## 🔍 コードレビュー — 第 N 周 / 全 3 周

**対象**: `<base>...<head>`（変更 X ファイル）
**判定**: ❌ 要修正

| 重大度 | 品質 | セキュリティ |
| --- | --- | --- |
| Blocker / Critical | 0 | 0 |
| High | — | 0 |
| Should fix / Medium | 0 | 0 |
| Consider / Low | 0 | 0 |

### 🚨 修正対象（Blocker・セキュリティ High 以上）
- [ ] `file:line` — 一文の要約
  - **再現**: 入力・状態 → 誤った結果
  - **検証**: 実行したコマンド → 結果

### 📋 報告のみ（今回は修正しない）
- `file:line` — 一文の要約

### ✅ 検証結果
- `npm test`: 34 件 / OK
- 描画時間: 10 回 0.46 秒（1 回あたり 46ms）

### 前周からの変化
- 解決: N 件 ／ 未解決: N 件（2 周連続で残る指摘には ⚠️）
```

### LGTM

```markdown
## ✅ LGTM — 第 N 周で完了

Blocker とセキュリティ High 以上の指摘はありません。

**対象**: `<base>...<head>`（変更 X ファイル）

### 検証結果
- `npm test`: 34 件 / OK
- 描画時間: 10 回 0.46 秒

### 残っている軽微な指摘（対応は任意）
- `file:line` — 一文の要約

### 周回の記録
| 周 | Blocker | Sec High+ | 対応 |
| --- | --- | --- | --- |
| 1 | 2 | 1 | 修正済み |
| 2 | 0 | 0 | LGTM |
```

### 打ち切り（3 周で解決しなかった場合）

```markdown
## ⚠️ 3 周で打ち切り — 未解決の指摘が残っています

**LGTM は出していません。** 以下は手動での判断が必要です。

### 未解決
- `file:line` — 一文の要約
  - 3 周で直せなかった理由

### 周回の記録
| 周 | Blocker | Sec High+ | 対応 |
| --- | --- | --- | --- |
| 1 | 2 | 1 | 一部修正 |
| 2 | 1 | 1 | 修正できず |
| 3 | 1 | 1 | 打ち切り |
```

### インラインコメント

```markdown
**[Blocker]** 一文の要約

**再現**: 入力・状態 → 誤った結果
**検証**: `コマンド` → 結果
**提案**: 直し方
```

重大度ラベルは `[Blocker]` / `[Should fix]` / `[Consider]`、セキュリティ側は `[Security: Critical]` / `[Security: High]` / `[Security: Medium]` / `[Security: Low]` を使う。

## スコープ外

初版では作らないと決めたもの。実装中に思いついても手を広げない。

- **他プロジェクトへの流用**（汎用化）— 審査項目をこのパッケージの不変条件に固定することが精度の源泉であり、汎用化するとその利点を失う
- **検証専用の第三エージェント**（指摘の反証役）— 各エージェントの自己検証で足りるかを先に見極める
- **CI からの自動起動** — まず手元で使って挙動を確かめる
- **レビュー結果の履歴保存** — PR のコメント欄が履歴として機能する

## 検証観点

実装後に以下を確認する。

- PR がない状態で起動したとき、ブランチ作成から draft PR 作成まで通ること
- 2 エージェントが並列に起動し、それぞれ独立した指摘を返すこと
- 指摘が 0 件のとき LGTM が投稿され、ループが 1 周で終わること
- Blocker を意図的に埋め込んだとき、修正 → 再レビュー → LGTM まで回ること
- 直せない Blocker を埋め込んだとき、3 周で打ち切られ LGTM が出ないこと
- 実際の `~/.claude/settings.json` が変更されていないこと
- 投稿されたコメントがテンプレートどおりの書式であること
